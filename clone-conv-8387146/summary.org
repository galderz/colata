** PR response draft
#+begin_src markdown
I made a mistake by blindly copying what was happening in aarch64 when I was trying to fix this bug,
and that is the cause of the issue with Unsafe.

With `VectorReduction2.byteXorBig` and the test cases first added in this PR,
the code path that was being tested is the one that has the shape of `AddP(AddP(reg, ConvI2L(idx)), off)`,
so I was really only tested the upper branch in the `if (off->is_Con()) {` of `Matcher::pd_clone_address_expressions`.

The Unsafe test case tests the `else` section, and in that case in x86 there is no benefit to cloning ConvI2L.
Whereas in aarch64 there is `indIndexI2L` which can match `AddP reg (ConvI2L ireg)`,
there is no equivalent in x86.

So, to fix the bug that Tobias noticed, I removed the `clone_conv` invocation in the `else`,
and added a comment to make it clear why `clone_conv` is not called.

While working on JDK-8351409, I decided to implement reassociation for all commutative AddNode instances,
as an experiment to see what the effects of reassociation would be beyond min/max long.

One thing that Emanuel observed in the benchmark results was that char/short demonstrated performance regression due to register spilling,
but byte didn't. E.g. in the xorBig use case.

The TLDR is  byte on x86 is not using the most optimal instruction operand to access data in the array.
This leads to additional instructions which create a throttle on the byteXorBig use case.
For char/short the optimal instruction kicks in, which means it takes full of advantage of reassociation,
but it's penalised by register spilling.
