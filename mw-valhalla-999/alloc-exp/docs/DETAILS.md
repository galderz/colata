# alloc-exp: details and reference

The entry point is [`../README.md`](../README.md): what to run and what you should see. This page
explains how it all works: recording mechanics, classification rules, analyzer options, probe
internals, the JDK build configuration, and caveats.

Goal: in a JVM running with `--enable-preview` (where `java.lang.Integer` and friends become value
classes), find **objects that C2-compiled code creates only because the class is a value class**.
Without preview these objects would not exist. Typical causes:
- C2 scalarized a value (it lives in registers),
- then had to create a heap copy ("materialize"/"buffer" it) because the value escapes,
- while in the identity world the same reference would just have been passed along.

Allocations made by the interpreter and by C1 count as warm-up noise and are reported but put aside.

Everything under `target/` is generated by the scripts below. `scripts/run-all.sh` regenerates it
(about 3 minutes); `scripts/run-probes-gdb.sh` adds the probe results (about 10 minutes).
Numbers quoted below come from one run. Re-runs differ slightly (JIT compilation timing changes how
much runs in the interpreter or C1), but the conclusions do not change.

### JDK build configuration

The JDK used for all results was configured with (from `CONFIGURE_COMMAND_LINE` in
`~/src/jdk/build/release-linux-x86_64/spec.gmk`; run from `~/src/jdk`):


(`--with-devkit=`, `--with-freetype-*=` and the `METAL`/`METALLIB`/`MIG`/`SETFILE` stubs were also
on the command line; they are irrelevant on Linux.) None of these options is needed here. The
debug info comes from configure **defaults**:

- `--with-native-debug-symbols` defaults to `external` on Linux.
  - HotSpot is compiled with `-g`, and the DWARF is split into `libjvm.debuginfo` (objcopy).
  - `libjvm.so` keeps its `.symtab`, which is enough for uprobes by symbol name, plus a
    `.gnu_debuglink` to the debuginfo file.
- For release builds, `--with-external-symbols-in-bundles` defaults to `none`, so
  `libjvm.debuginfo` is *not* copied into `images/jdk`. It stays in
  `~/src/jdk/build/<conf>/support/modules_libs/java.base/server/libjvm.debuginfo`. That is where
  `scripts/env.sh` looks; spec.gmk shows `COPY_DEBUG_SYMBOLS=true` and an empty `SHIP_DEBUG_SYMBOLS`.

Debug info is needed only by `scripts/offsets.sh` (struct offsets) and `scripts/probe-gdb.sh`. The
uprobes themselves only need `libjvm.so`'s symbol table. Alternatives when building a JDK for this:

| configure option | where the DWARF ends up | picked up by `env.sh` |
|---|---|---|
| (default) `--with-native-debug-symbols=external` | `support/.../libjvm.debuginfo` | yes, via `<JAVA_HOME>/../../support/...` |
| `--with-external-symbols-in-bundles=full` | also `images/jdk/lib/server/libjvm.debuginfo` | yes |
| `--with-native-debug-symbols=internal` | inside `images/jdk/lib/server/libjvm.so` | yes (`.debug_info` section detected) |
| `--with-native-debug-symbols=none` | nowhere | no: offsets/gdb probe unavailable |

A JDK whose debuginfo lives elsewhere (e.g. a distro `-debuginfo` package) works with
`LIBJVM_DEBUGINFO=/path/to/libjvm.so.debug`. If no debug info is available, the four values in
`target/offsets.env` can be written by hand, but only for exactly the same build.

## The scenarios (`src/ValueAllocs.java`)

Each scenario stores `java.lang.Integer`s into an `Object[]` in a hot loop
(`<iterations>` × `-Dinner=N`, default 50 × 1,000,000). Mode `identity` = no flags; mode `preview` =
`--enable-preview`. Every run uses Epsilon GC (`-XX:+UseEpsilonGC`), so nothing is ever freed.
`-XX:CompileCommand=dontinline,ValueAllocs::id` keeps `id()` a real call.

| scenario | code | identity world | value world (preview) | extra objects? |
|---|---|---|---|---|
| `fresh` | `sink[i] = box(i + 1000)` | `new Integer` in `Integer.valueOf` | C2 scalarizes the box and materializes it at the `aastore` | **no**: same count, moved |
| `cached-call` | `sink[i] = id(Integer.valueOf(i & 63))` | cached boxes, nothing allocated | `id()` takes and returns the value scalarized; the caller must create a new heap copy at the `aastore` | **yes** |
| `flat-field` | `h.v = Integer.valueOf(..&63)` then `sink[i] = h.v` | the field holds a reference to a cached box | the `Integer` field is flattened into `Holder`; reading it and letting it escape requires a new heap copy | **yes** |

## 2. Recording stack traces

### How the stack traces are obtained

Both tools record an event when an allocation reaches the HotSpot runtime, and walk the stack there:
- **JDK JFR** (`jdk.ObjectAllocationSample`, `jdk.ObjectAllocationOutsideTLAB`):
  - `MemAllocator` sends the event on a TLAB refill or an outside-TLAB allocation.
  - The JFR stack walker starts at the last Java frame, so HotSpot's C++ frames are never
    recorded.
  - Each frame has a method, a bci, a line, and a type: `Interpreted`, `JIT compiled`,
    `Inlined` or `Native`. C1 and C2 are not distinguished.
- **async-profiler** (`event=alloc`):
  - Uses JVMTI `SampledObjectAlloc`. In `cstack=vmx` mode (= `cstack=vm,features=mixed`) it walks
    a *mixed* stack with HotSpot's VM structs.
  - The stack includes the C++ and stub frames between the Java code and the allocator, e.g.
    `new_instance_blob (C2 runtime)` / `OptoRuntime::new_instance_C`, or
    `store_value_type_fields_to_buf_blob`.
  - C1 frames are labelled `C1 compiled`, C2 frames `JIT compiled`; inlined frames are `Inlined`.
  - The default `cstack=vm` records only Java frames without the C1/C2 distinction.

### `scripts/record-jfr.sh <scenario> <identity|preview> <sampled|exact> [iterations]`

- `sampled`: `jdk.ObjectAllocationSample` throttled to 10000/s. Each event has a *weight* (the bytes
  it stands for), so sums estimate allocated bytes. 50 iterations by default.
- `exact`: `-XX:-UseTLAB`. Every allocation (interpreter, C1, C2 inline fast paths) takes the runtime
  slow path and emits one `jdk.ObjectAllocationOutsideTLAB` event, so **events = objects**.
  - 3 iterations by default; about 3 s and 50 MB per recording.
  - `-XX:-UseTLAB` acts in C2 macro expansion (`macro.cpp`, "Force slow-path allocation"), *after*
    escape analysis and scalarization, so it does not change which allocations C2 keeps.
- Runs with `-XX:-TieredCompilation` so that every `JIT compiled` frame is C2. Use `TIERED=1` to keep
  tiered compilation; the analyzer then reports `JIT(C1|C2)`.
- Output: `target/jfr-<variant>/<scenario>-<mode>.jfr`.

### `scripts/record-ap.sh <scenario> <identity|preview> [iterations=50]`

- `-agentpath:libasyncProfiler.so=start,event=alloc,alloc=128k,cstack=vmx,file=<out>.jfr`
- Tiered compilation stays on, because async-profiler labels C1 frames itself.
- Output: `target/ap/<scenario>-<mode>.jfr`.

## 3. Analyzing recordings: `tools/AllocAnalyzer.java`

`top.py` from the first exploration is gone; this analyzer replaces it. It reads JDK JFR and
async-profiler JFR files with `jdk.jfr.consumer`. It reads class files with the ClassFile API to
decode the bytecode at each bci and to decide whether the allocated class is a value class. It
reads them from the analyzed JDK's `jrt:/` filesystem (in preview mode, with the
`META-INF/preview` variants such as value class `Integer`) and from `--cp`.

```
scripts/analyze.sh target/jfr-exact/cached-call-preview.jfr            # wrapper: adds --cp, --preview, --baseline
java tools/AllocAnalyzer.java --cp build/classes --preview \
     --baseline target/ap/cached-call-identity.jfr target/ap/cached-call-preview.jfr --top 5
```

| option | meaning |
|---|---|
| `--cp p1:p2` | application classes/jars, to decode bytecodes of application methods |
| `--preview` / `--no-preview` | the recorded JVM ran with/without `--enable-preview`. Auto-detected for JDK JFR (`jdk.JVMInformation`); async-profiler recordings need it. `analyze.sh` derives it from `*-preview.jfr` / `*-identity.jfr` |
| `--jit-is-c2` | treat `JIT compiled` as C2. Automatic for async-profiler vmx recordings and `-XX:-TieredCompilation` runs |
| `--baseline id.jfr` | identity recording of the same workload: prints the **extra** allocations per (class, C2 compilation unit) |
| `--top N`, `--depth N`, `--all`, `--native`, `--class S` | number of stacks; Java frames per stack; include interpreter/C1 stacks; show all native frames; filter by class name |

### Classification of each allocation

1. Tier: find the first Java frame. If it is `Inlined`, follow the inlined frames down to the
   compilation root (the "compilation unit"). The root's type is the tier: `Interpreted` →
   *Interpreter (ignored)*, `C1 compiled` → *C1 (ignored)*, `JIT compiled` → C2.
2. For C2 allocations:
   - **`C2 identity object`**: the allocated class is an identity class.
   - **`C2 value object: MATERIALIZED at <bytecode>`**: a value-class object whose allocating
     frame's bci is *not* a `new`. C2 had the value scalarized and created a heap copy at the
     point where it escapes (`aastore`, `putfield`, `areturn`, `invoke*`, ...). This is
     `ValueTypeNode::buffer`; the debug info of that allocation is the escaping bytecode.
   - **`C2 value object: allocated at new`**: the `new` itself survived (for example, the value
     escapes before C2 could scalarize it). The identity world allocates there too.
   - **`C2 value object: rematerialized on deoptimization`**: native frames show
     `Deoptimization::*` (async-profiler only).
3. *Materialized* does not by itself mean *extra*. In `fresh` the object exists in both worlds; only
   the allocation point moved. Extra objects show up in the `--baseline` diff: allocations per
   (class, C2 compilation unit) in the preview run minus the identity run.

## 4. Probes: exact counts per HotSpot runtime entry point

The probes answer "which HotSpot entry point allocated this?" with exact counts, without stack walks:
- The JVM runs with `-XX:-UseTLAB`, so every allocation goes through the runtime.
- A probe on `InstanceKlass::allocate_instance` reads the class name through `Klass::_name`.
- The allocation is attributed to the runtime entry point active on the thread:

| context | entered from |
|---|---|
| `C2  OptoRuntime::new_instance_C`, `C2  OptoRuntime::load_unknown_value_C`, `C2  Deoptimization::realloc_*` | C2 code only |
| `C1  Runtime1::new_instance` | C1 code only |
| `INT InterpreterRuntime::_new`, `read_flat_field`, `flat_array_load` | interpreter only |
| `ANY SharedRuntime::store_value_type_fields_to_buf`, `allocate_value_types` | shared stubs: interpreter, C1 or C2 |

- For C2 allocations the probe also reads the return pc into the calling nmethod: `last_Java_sp[1]`,
  because the C2 runtime stub frame is 2 words on x86_64.
- `probe-report.py` resolves that pc to the compiled method using `/tmp/perf-<pid>.map`, written by
  `-XX:+DumpPerfMapAtExit`.
- Only instance allocations are counted (arrays go through other entry points).
- Struct offsets come from `scripts/offsets.sh`. They differ between builds:
  `KLASS_NAME=24 SYMBOL_LENGTH=4 SYMBOL_BODY=6 THREAD_LAST_JAVA_SP=1128` for this build.

The probes show *where in HotSpot* an allocation is made. They cannot tell an extra object from a
moved one: `fresh` and `cached-call` look the same here. That needs the identity baseline from
section 3.

`cached-call-identity.txt` has no `java.lang.Integer` line at all; everything is interpreter start-up.

In the preview run, the `ANY store_value_type_fields_to_buf` allocations come from the interpreter.
Interpreted `cachedCall` calls the C2-compiled `id()`, which returns the `Integer` scalarized, and
the interpreter needs a heap object. This was verified by resolving the stub's return address:
`last_Java_sp[17]` (18-word stub frame) points into `Interpreter`. Those allocations are warm-up
noise; in C2 code the same situation is handled by the materialization at the `aastore`.

### Outside a container: `scripts/probe-bpf.sh <scenario> <mode> [iterations=5] [inner=1000000]`

**Status:** works in an isx VM instance (`type: vm` template): kernel 7.3.5, Fedora 45,
bpftrace v0.26.0 (`target/probe-bpf-env.txt`). Results are in the README, step 6. The first attempt
on a host had crashed bpftrace (SIGSEGV); background, the `scripts/bpf-smoke.sh` bisection and the
task list are in `docs/bpf-context.md`.

It cannot run in an unprivileged container. The logic is identical to the gdb version.
Requirements: Linux with uprobes, bpftrace (tested with v0.26.0), root, and the JDK plus
`libjvm.debuginfo` (only for `offsets.sh`). BTF is not needed: the VM kernel has no
`/sys/kernel/btf/vmlinux` and the probe works. On a host or VM with this directory and the JDK:

```
sudo dnf install bpftrace gdb          # or apt install bpftrace gdb
scripts/build.sh
sudo -E scripts/probe-bpf.sh cached-call preview      # -E keeps JAVA_HOME_EXP etc.
sudo -E scripts/probe-bpf.sh cached-call identity
```

What the script does:
- Substitutes the `libjvm.so` path and offsets into `probe/alloc_ctx.bt.in`, giving
  `target/probe-bpf/alloc_ctx.bt`.
- Starts the JVM through `bpftrace -c`, so every probe is filtered on its pid (`cpid`).
- Copies the perf map and prints the same report as the gdb version.

To trace an already-running JVM instead, replace `cpid` with the target pid and use
`bpftrace -p <pid>`. That JVM must have been started with `-XX:-UseTLAB` for exact counts. Without
it, only TLAB refills reach the runtime, which gives samples, not counts.

Each allocation costs three uprobe hits (entry, return, `allocate_instance`). Measured in the VM:
~15 s for a preview run with ~5.1M allocations vs ~0.5 s without the probe, i.e. ~3 µs per
allocation (including ~2 s of bpftrace start-up).

bpftrace caveats (seen with v0.26.0, both fixed in the scripts):
- `str(ptr, n)` counts the terminating NUL in `n`, so a length read from a HotSpot `Symbol` must be
  passed as `len + 1`; otherwise the last character of every class name is cut off.
- `bpftrace -c "<cmd>"` turns each extra space into an empty argument, which the `java` launcher
  rejects; `probe-bpf.sh` collapses repeated spaces in the command line first.

## Corrections to the first exploration

- async-profiler *does* attribute allocations to tiers and HotSpot layers, but only in
  `cstack=vmx` mode. JDK JFR does not.
- The earlier "value-object buffer vs larval buffer" wording is replaced by the classification
  above. What matters is whether the C2 allocation sits at the value's `new`, or is a
  materialization of a scalarized value at an escape point. Whether that object is *extra* is
  decided by the identity baseline.
- `store_value_type_fields_to_buf` is not only an interpreter/C1 path. When a C2 caller needs a
  heap object for a value returned scalarized, it allocates inline (TLAB fast path plus the pack
  handler, `macro.cpp` around line 2889) and falls back to that stub. So under a C2 frame the stub
  is a C2 signal. In these scenarios it showed up only from the interpreter (warm-up).

## 5. Applying this to the real workload

1. Record the identity and preview runs with async-profiler:
   `-agentpath:<ap>/libasyncProfiler.so=start,event=alloc,cstack=vmx,file=<name>-identity.jfr`
   (and `-preview.jfr`). For exact counts, record with JFR instead:
   `-XX:-UseTLAB -XX:StartFlightRecording:filename=...,settings=default,jdk.ObjectAllocationSample#enabled=false,+jdk.ObjectAllocationOutsideTLAB#enabled=true`.
   That costs one event per allocation, so keep the run short.
2. `java tools/AllocAnalyzer.java --cp <app jars> --preview --baseline <name>-identity.jfr <name>-preview.jfr --class java.lang.Integer`
3. Look at the `MATERIALIZED at <bytecode>` stacks and at the compilation units with large
   `extra` values.
